Auditoría Operativa - Aeropuerto La Rioja

Descripción General

La aplicación es un sistema completo de auditoría operativa para el Aeropuerto La Rioja (IRJ) que funciona como una Progressive Web App (PWA) con capacidades offline. Evalúa múltiples aspectos del servicio (limpieza, niveles de servicio, infraestructura) y genera certificaciones mensuales.

Stack Tecnológico:
  • Backend: Python 3 (sin frameworks externos) + SQLite3
  • Frontend: JavaScript vanilla + PWA (Service Worker)
  • Servidor HTTP: http.server de la biblioteca estándar
  • Base de datos: SQLite 3 (archivo local)
  • Autenticación: Token-based (Bearer tokens en memoria)

Módulos Clave y Responsabilidades

1. calc.py — Motor de Cálculo Puro ⭐

Líneas de código: ~717
Responsabilidad: Todas las fórmulas matemáticas de auditoría
Entrada/Salida: Funciones sin estado (no acceden BD ni sesión)

Componentes principales:

Función Propósito Input Output
sector_limpieza() Score de limpieza por control diario Ítems, desvíos, estado 0.0 - 1.0 o None
sector_mensual() Promedio de días auditados del mes Lista de scores diarios Promedio ponderado
completitud_mes() Cobertura de auditoría del período Días auditados, período Detalles de cobertura
certificacion_mensual() % final de pago (6 ítems ponderados) Ítems con valores Certificación con detalles
item_calidad_servicio() Calidad ajustada por no conformidades Estado, NCs, penalización Score final ajustado
resultado_los() Porcentaje global Niveles de Servicio Items LoS evaluados % cumplimiento LoS
✓ Característica crítica: Todas las funciones son puras (sin efectos colaterales). Pueden ser testeadas sin BD, son determinísticas y se usan tanto en backend como en frontend.

2. api.py — API REST y Enrutador

Líneas de código: ~1000+
Tecnología: http.server (stdlib), sin FastAPI/Flask
Autenticación: Bearer tokens en memoria

Endpoints principales:

Método Ruta Función
POST /api/login Autenticación de usuario
GET /api/control/{id} Obtener control en curso
POST /api/control/{id}/sector Guardar sector evaluado
GET /api/certificacion/{mes} Cálculo mensual (llama a calc.py)
GET /api/config Obtener configuración editable
POST /api/config Guardar configuración (validada)
GET /api/informes/{mes} Generar reporte del mes

3. db.py — Operaciones de Base de Datos

Patrones: Context managers, prepared statements, transacciones
Seguridad: Hashing de passwords (bcrypt), SQL injection prevention
Funciones clave: Crear usuario, registrar auditoría, guardar control

4. validacion.py — Validación Exhaustiva

Valida toda entrada editable por el admin antes de guardar:

  • Ponderaciones (deben sumar 100%)
  • Rangos térmicos (mín < máx)
  • Inventarios (cantidades coherentes)
  • Umbrales PCI, iluminación, elevación
Validación defensiva: Una ponderación negativa o un rango invertido nunca llega a la BD ni afecta los cálculos.

5. services.py — Lógica de Negocio

Coordina acceso a BD, validación y cálculos:

  • Crear nuevos períodos de auditoría
  • Guardar hallazgos del auditor
  • Generar reportes
  • Registrar auditoría de cambios

6. Frontend: app.js + PWA

Tipo: Progressive Web App vanilla (sin React/Vue)
Estado: Indexado en IndexedDB para uso offline
Sincronización: Cola automática cuando vuelve la conexión

Módulos frontend clave:

  • app.js — Router hash (#/control/123), sesión de usuario
  • store.js — IndexedDB: caché de controles, fotos, cola sync
  • sync.js — Detecta red, encola cambios offline, replica al ir online
  • calc.js — Duplica funciones de calc.py en JavaScript
  • sw.js — Service Worker para caché, offline

Características Offline

  • Almacenamiento local: IndexedDB (sin límite práctico)
  • Fotos: Se cacheaban en base64, se sincronizan cuando hay red
  • Sesiones: Token se guarda localmente, se renueva al conectar
  • Cola de sincronización: Automática, retry con backoff
  • Service Worker: Sirve recursos en caché, fallback offline
✓ Caso de uso: Un auditor en la pista sin señal puede cargar todos los hallazgos del día, y al volver al área con WiFi la app sincroniza automáticamente sin intervención.

Consideraciones de Seguridad

Autenticación

  • Tokens Bearer de 32 bytes (secrets.token_urlsafe)
  • En memoria (se pierden al restart)
  • Duración: 30 días desde último uso
  • Passwords: hasheadas con verificación constante (timing-safe)

SQL Injection

  • Prepared statements en todas las queries
  • Parámetros vinculados (?, ?, ?)
  • No concatenación de strings

XSS (Frontend)

  • Escapeo de HTML en UI.esc()
  • textContent en lugar de innerHTML donde sea posible
  • No eval() ni dynamic code execution
⚠️ Nota: Los tokens en memoria se pierden al reiniciar. En una tablet con uptime prolongado, eso es aceptable. En un servidor de producción sería un problema.

Estructura de BD

SQLite3 automáticamente crea las tablas en primer inicio:

  • usuarios — auditor, admin, contrasenias
  • sesiones — tokens activos
  • periodos — meses auditados
  • controles — cada día de auditoría
  • sectores — resultado por sector/día
  • fotos — referencias a imágenes
  • configuracion — parámetros editables
  • auditoría — historial de cambios

Puntos de Extensión

1. Nuevos Cálculos (Sin BD)

Agregar función en calc.py, testear independientemente, reutilizar en frontend (calc.js).

2. Nuevos Parámetros Editables

Agregar en validacion.VALIDADORES, crear endpoint en api.py, actualizar BD.

3. Nuevos Ítems del Check-list

Actualizar esquema BD, agregar a UI, la lógica de cálculo (promedio de confirmados) es genérica.

4. Integración con Sistemas Externos

Agregar endpoint POST en api.py que reciba datos de otra aplicación, validar, guardar, recalcular.

5. Exportación a Otros Formatos

Reutilizar informes.py, generar CSV, JSON, exportar a Excel.

Conclusiones Técnicas

✓ Arquitectura sólida: Separación clara entre lógica pura (calc.py), API (api.py), BD (db.py) y UI (frontend).
✓ Seguridad: Validación en capas, prepared statements, tokens seguros, auditoría completa.
✓ Offline-first: Funciona sin red, sincroniza automáticamente, maneja conflictos.
✓ Testabilidad: Funciones puras, fixtures de BD, tests por módulo.
⚠️ A considerar en producción:
  • Tokens en memoria: revisar para deployment de larga duración
  • SQLite: adecuado para un aeropuerto pequeño, escalabilidad limitada a ~100 usuarios concurrentes
  • PWA sin HTTPS en desarrollo: en producción asegurar certificado válido
  • Backup automático: considerar policy de respaldos

Fortalezas

  • Cero dependencias externas en backend (solo stdlib Python)
  • Lógica de cálculo portable (se usa en backend y frontend sin cambios)
  • PWA sin frameworks pesados (vanilla JS)
  • Base de datos transaccional (ACID compliance)
  • Suite de tests completa para módulos críticos

Áreas de Mejora Futuro

  • Migración a framework web si escala (FastAPI, Django)
  • PostgreSQL para multi-usuario en producción
  • Testing end-to-end con Selenium/Playwright
  • Monitoreo y alertas (Sentry, DataDog)
  • CI/CD pipeline (GitHub Actions, GitLab CI)
